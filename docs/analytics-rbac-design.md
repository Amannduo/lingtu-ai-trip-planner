# 智能旅行数据分析与权限设计

## 1. 目标

智能分析不直接把自然语言转换成任意 SQL，而是先把问题解析成受支持的分析意图、时间范围和指标，再由服务端权限策略确定数据范围，最后执行只读、参数化、白名单查询。

核心目标：

- 每个结论都能追溯到真实查询结果、时间范围和样本量。
- `user`、`manager`、`admin` 的数据边界由后端强制执行，不信任前端传入的角色或用户 ID。
- 数据不足时明确提示，不输出看似精确但没有统计基础的预测。
- 图表、表格和文字摘要使用同一份查询结果，避免三者口径不一致。
- 模拟数据始终保留 `source` 标记，可与真实生成数据分开统计。

## 2. 分析执行链路

```text
用户问题
  -> SecurityAgent：敏感字段和危险操作检查
  -> IntentAgent：识别指标、维度、时间范围和比较方式
  -> PolicyAgent：根据登录用户角色生成服务端数据范围
  -> AnalyticsAgent：执行白名单、参数化、只读查询
  -> QualityAgent：计算样本量、覆盖区间、缺失率和可用性
  -> ChartAgent：从查询结果生成 ECharts 配置
  -> ReportAgent：结合真实数字、范围和质量提示生成结论
  -> AuditAgent：记录问题、意图、工具、授权结果和查询摘要
```

LLM 可以用于意图理解和自然语言润色，但不能自行扩大数据范围，也不能绕开查询白名单。

## 3. 角色权限矩阵

| 能力 | user | manager | admin |
| --- | --- | --- | --- |
| 本人旅行画像、目的地、预算趋势 | 允许，仅本人 | 允许 | 允许 |
| 全站目的地、月份、季度匿名汇总 | 禁止 | 允许 | 允许 |
| 趋势与热度预测 | 仅本人数据且满足样本门槛 | 允许匿名汇总 | 允许 |
| 逐条旅行计划明细 | 仅本人 | 禁止 | 允许，默认不含敏感字段 |
| 用户级明细、联系人、手机、邮箱 | 禁止 | 禁止 | 智能分析默认禁止 |
| 查询日志与审计日志 | 禁止 | 禁止 | 允许 |
| 数据质量与来源统计 | 仅本人可见范围 | 全站汇总 | 全站与审计视图 |

补充规则：

- `user` 的任何分析查询都必须附加 `user_id = 当前会话用户`，与问题是否包含“我的”无关。
- `manager` 只能获得聚合结果，不返回计划号、用户 ID、自由文本或完整计划 JSON。
- `admin` 的明细查询也只返回业务分析白名单字段；PII 不进入自然语言分析链路。
- 所有权限判断使用后端会话中重新加载的账号角色。

## 4. 时间与统计口径

支持本月、上月、本季度、上季度、本年、去年、去年同期和全部历史。旅行去向按 `travel_plans.start_date` 归属统计周期；计划量按旅行计划记录数统计；目的地数按去重目的地统计；预算默认使用计划预算，实际消费仅在 `actual_cost` 有足够数据时启用。

同比比较使用去年相同自然时间区间，环比比较使用前一个完整自然周期。返回结果必须携带实际起止日期，避免只显示“本季度”而无法复核。

## 5. 数据质量门槛

每次分析返回可见计划数、用户数、目的地数、最早和最晚出发日期、数据来源、关键字段完整率、当前查询样本量以及质量警告。

- 少于 3 条：只展示事实记录，不做趋势判断。
- 少于 12 条或不足 3 个自然月份：不做月度预测。
- 没有覆盖去年同期：不计算同比。
- `actual_cost` 有效率不足 60%：不输出实际消费结论。
- 完整行程内容覆盖不足 60%：只使用目的地、日期、预算等结构化字段。

## 6. 当前数据库基线

系统实际运行连接由 `DATABASE_URL` 决定。本次审计发现运行环境使用 PostgreSQL，而 `backend/data/travel.db` 是备用本地 SQLite，两者不是同一个数据集。

改造前的运行 PostgreSQL：

- 旅行计划 53 条、计划用户 28 个、目的地 28 个，日期覆盖 2025-01-03 至 2026-10-04。
- 其中 49 条为模拟数据，真实生成记录很少，仍不足以稳定展示分组趋势。

补充开发演示数据并迁移备用 SQLite 记录后：

- 保留真实/个人计划不动，将 `realistic_synthetic` 模拟计划补到 1000 条。
- 将备用 SQLite 中的 7 条 `generated` 计划按 `plan_no` 去重迁入 PostgreSQL，来源标记为 `sqlite_migrated/generated`，SQLite 原记录继续保留。
- 当前共 1010 条计划、456 个计划用户、36 个目的地，日期覆盖 2025-01-01 至 2026-10-06，可演示季度、同比和绘图。
- 模拟数据占比约 99.0%，完整 `plan_json` 共 7 条、覆盖约 0.7%；这些数据只能用于功能演示，不能作为真实经营结论。

备用本地 SQLite 的保留基线：

- 旅行计划 7 条，关联用户 1 个，用户画像 1 条。
- 目的地 5 个，日期仅覆盖 2026-07-11 至 2026-07-17。
- 实际消费缺失 7 条，完整计划 JSON 缺失 3 条。
- 查询日志和审计日志均为 0。

生产统计必须逐步积累真实计划，并按 `source` 排除模拟记录；前端与回答都会显示来源和模拟数据告警。

## 7. API 契约

- `POST /api/agent/chat`：执行受权限约束的分析；`extra.analysis` 返回范围、周期、样本量和质量提示。
- `GET /api/agent/capabilities`：返回当前角色允许的分析能力、限制和建议问题。
- `GET /api/agent/data-status`：返回当前角色可见数据的覆盖、来源和质量状态。

前端只用这些接口解释能力和展示结果；真正的数据过滤和权限判定始终在后端完成。
